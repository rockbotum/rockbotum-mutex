# rockbotum-mutex

Репозиторий с различными реализациями мьютексов на Go — для изучения и сравнения
подходов к синхронизации.

Цель — не заменить `sync.Mutex`, а понять, почему он устроен именно так: чем
оборачивается spin lock, зачем нужен `runtime.Gosched`, что даёт ticket lock и
почему condition variables остаются лучшим выбором для RW-семантики.

## Структура

```
.
├── README.md
├── go.mod
├── spinlock/               # CAS-spinlock без уступки процессора
├── spinlock-runtime-call/  # CAS-spinlock с runtime.Gosched
├── retry-mutex/            # CAS-spinlock с ограниченным числом попыток
├── ticket-lock/            # Ticket lock, гарантирует FIFO
├── peterson-mutex/         # Ровно два участника, явные индексы
├── rw-mutex/               # RW-мьютекс на sync.Cond
├── mutex-with-action/      # Выполняет действие под локом
├── benchmark/              # Сравнение с sync.Mutex
└── .opencode/              # Локальная конфигурация агентов (в git не отслеживается)
```

## Реализации

| Пакет | Идея | Гарантии | Ограничения |
|---|---|---|---|
| `spinlock` | Чистый CAS-цикл, `atomic.Bool` | Взаимное исключение | Жжёт CPU, не уступает планировщик |
| `spinlock-runtime-call` | CAS-цикл с `runtime.Gosched()` | Взаимное исключение | Уступает планировщик на каждой попытке |
| `retry-mutex` | До 3 попыток CAS, затем `Gosched` | Взаимное исключение | Больше кода, поведение близко к варианту с `Gosched` |
| `ticket-lock` | Каждый берёт билет, ждёт свою очередь | Взаимное исключение + **FIFO** | Плохо масштабируется, convoy-эффект |
| `peterson-mutex` | Два флага `wants` + `victim` | Взаимное исключение | **Только 2 участника**, индекс передаётся явно |
| `rw-mutex` | `sync.Cond` поверх `sync.Mutex` | RW-семантика, параллельные читатели | Возможен голод читателей |
| `mutex-with-action` | CAS + выполнение `func() any` под локом | Взаимное исключение | `Lock()` **не отпускает** лок — нужен явный `Unlock()` |

### Важные детали

**`peterson-mutex`** — не алгоритм Петерсона в классическом смысле, а TTAS
(test-and-test-and-set) с полем `victim`. Массив `wants[2]` жёстко ограничивает
число участников двумя, а `Lock(index int)` требует передать свой индекс явно.
Для произвольного числа горутин использовать нельзя.

**`mutex-with-action`** — `Lock(action)` захватывает лок, выполняет действие и
возвращает результат, но **не освобождает** лок. Забытый `Unlock()` навсегда
блокирует мьютекс. Это осознанный trade-off: невозможно случайно выполнить
действие вне критической секции, но легко получить дедлок.

**`rw-mutex`** — при `Unlock()` делается безусловный `Broadcast()`, поэтому
проснуться могут и писатели, и читатели, не прошедшие проверку. Это корректно,
но дороже точечного `Signal()`.

## Запуск

```bash
go build ./...
go vet ./...

# Тесты
go test ./...

# Тесты с детектором гонок (нужен C-компилятор, см. ниже)
go test ./... -race

# Бенчмарки
go test ./benchmark -bench=. -benchmem
```

### Ограничение: `-race` на Windows

Детектор гонок требует cgo, а значит C-компилятор. Если его нет, `-race`
не запустится:

```
go: -race requires cgo; enable cgo by setting CGO_ENABLED=1
```

Установи MinGW-w64 (например, `winget install BrechtSanders.WinLibs.POSIX.UCRT`)
и убедись, что `gcc` доступен в `PATH`. Тесты специально спроектированы так,
чтобы ловить нарушение взаимного исключения и без `-race`: внутри критической
секции стоит неатомарный счётчик, расхождение которого означает, что секцию
выполняли две горутины одновременно.

## Результаты бенчмарков

AMD Ryzen 5 2600X, Windows, `GOMAXPROCS=12`, `go1.27.1`. Числа сильно зависят от
железа и нагрузки — приводится как иллюстрация, а не как истина.

**Без конкуренции** (ns/op) — все реализации на уровне `sync.Mutex`:

| Реализация | ns/op |
|---|---|
| `sync.Mutex` | 13.97 |
| `spinlock` | 14.02 |
| `ticket-lock` | 14.12 |
| `retry-mutex` | 14.31 |
| `spinlock-runtime-call` | 14.39 |

**С конкуренцией** (ns/op) — здесь начинаются различия:

| Реализация | ns/op | Комментарий |
|---|---|---|
| `spinlock-runtime-call` | 20.60 | Лучший: уступает планировщик, не ворует CPU у владельца |
| `retry-mutex` | 23.40 | Практически то же, что и вариант с `Gosched` |
| `sync.Mutex` | 39.33 | Дороже, но предсказуемо |
| `spinlock` | 216.80 | **В 5 раз хуже**: горутины крутят цикл и мешают владельцу |
| `ticket-lock` | 14309 | **Худший**: каждый `Unlock()` будит всех ожидающих |

Главный вывод: чистый spin lock проигрывает не из-за CAS, а из-за отсутствия
уступки планировщику. На многоядерной машине ожидающие горутины занимают ядра,
которые нужны держателю лока. Одно `runtime.Gosched()` в цикле меняет картину
радикально — именно поэтому в `sync.Mutex` переключение режима стоит так дёшево.

**RW-мьютекс** (ns/op):

| Сценарий | `sync.RWMutex` | `rw-mutex` |
|---|---|---|
| Чтение | 30.18 | 91.16 |
| Запись | 61.77 | 164.3 |

`sync.Cond` дороже встроенного `sync.RWMutex`, но даёт тот же параллелизм
читателей, который проверяет тест `TestReadConcurrency`.

**Прочие**: `mutex-with-action` — 14.48 ns/op без конкуренции, 20.45 ns/op с
конкуренцией. `peterson-mutex` — 310 ns/op на две горутины (сравнение с
остальными некорректно: другое число участников).

## Требования

Go 1.24+ (используется `b.Loop()` в бенчмарках). Модуль объявляет `go 1.27.1`.
